## Mandatory hosted preflight — prepared locally, not executed

Before EVERY separately approved hosted application of 34, including a rehearsal
or idempotency re-run, the approved read-only workflow must:

1. Independently verify project ref, region and ACTIVE_HEALTHY status against the
   approved environment record. Use that same approved ref for project metadata
   and the database query; current_database() alone never identifies a project.
2. Execute checks/h9_hosted_preflight.sql with read_only:true. Capture the result,
   readOnly:true and the exact SQL SHA-256 in a private evidence envelope:
   {project:{id,region,status},capture:{projectRef,sqlSha256,readOnly},snapshot:{...}}.
   This is a capture contract, not cryptographic server attestation.
3. Evaluate it OFFLINE:
   node scripts/h9-f12-hosted-preflight.mjs --expected-project-ref <approved-ref>
     --expected-region <approved-region> --evidence <private-capture.json>
4. Stop on nonzero exit, missing inventory, unknown shape, mandatory failure,
   absent supabase_admin or any profile drift. Never repair defaults to pass.
5. Review recorded ownership, membership, publication and rolconfig observations.
   An evaluator PASS covers mandatory F12 predicates; it does not approve those
   observations or authorize hosted operations. Preserve the founder review gate.
6. Only under the separate application approval: dry-run, apply, then all 15
   postmigration checks. Preflight permits the table/sequence grants X1/34 must
   repair; postmigration checks require their absence.

The evaluator has no network path, secret input or remote flag. CLI output omits
rolconfig values; the private capture retains them for hosted security review.
rolconfig is observational, outside F12 enforcement. Database ownership generally,
publication scope and harmless membership existence are also observational;
the migration enforces only their approved effective-privilege consequences.

## Remaining approvals and limitations

X2 still permits future supabase_admin-created public objects to receive broad
API grants. Detection does not prevent that creation or repair a pre-existing
unsafe role configuration. A refused migration leaves unsafe state unchanged;
operator containment/remediation requires its own authorized action.

PROD approval requires a separate exposure-control decision and explicit residual
X2 risk acceptance. Before that approval, record founder-only administrative access,
approved platform-change procedures with before/after public inventories and all
15 checks, maintenance-triggered detection, and an approved incident-containment
procedure. Scheduled detection needs separate credential/alerting authorization.
Those operational controls are requirements, not completed or technically enforced
by this local change. The deployment runbook records their application gates.

C4, Data API disabling, F14, H-11 and hosted/production execution remain separate.
Existing function ACLs, including their grant options, are preserved; R4's grant
option controls cover tables, columns, sequences and judged defaults. R4 does not
claim comprehensive existing-function ACL hardening.
A PostgREST hook is not a cross-product control. Disabling the Data API affects
existing admin/Edge service-role paths. Realtime signal limitations remain;
pull is the data path.

Supabase's published transition reaches existing projects on 2026-10-30:
https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically
Existing table grants are retained. The announcement does not establish the
resulting exact supabase_admin profile. Any wider, narrower or missing profile
requires new measurement, review and approval; no automatic re-baselining.
