### CHANGED CONTRACTS

1. **Sellable FEFO:** a dated batch remains sellable through its printed expiry date and is hard-blocked when `expiry_date <` the current Asia/Dhaka business date. Null expiry is sellable and sorts after every dated batch. Search, scan, cart, inventory sellable totals, notifications, promotion, and checkout share this rule.
2. **Batch pricing and refresh:** checkout consumes FEFO batches at each batch’s current effective integer-paisa price and persists one sale-item row per consumed batch. Cart totals are previews. Checkout re-reads stock, expiry, base price, and promotion inside the local workflow; any changed allocation or total blocks completion, displays the refreshed quote, and requires explicit reconfirmation.
3. **Promotion then discount:** base batch sale price → per-batch promotion → promoted subtotal → sale-level amount/% checkout discount. Promotion percentages and sale-discount percentages are integer basis points; effective price and discount are resolved to paisa with named integer rounding. The sale discount may reach but never exceed the promoted subtotal. Largest-remainder allocation is proportional to promoted batch-line totals, with stable batch/item ID tie-breaks and an exact header/line sum assertion.
4. **Promotion lifecycle:** at most one active promotion per shop+batch. Apply/replace/reverse is audited; reversal deactivates rather than deletes. Base batch price never changes. Promotion is permitted only for dated, non-expired Near/Far batches and requires both `expiry_manage` and `sale_discount`; it ceases to affect price once the batch expires.
5. **Split:** Split means `cash_applied + customer_credit = final_total`, with a required same-shop customer, `0 < cash_applied < final_total`, and no change/over-tender. Zero cash uses Credit; full cash uses Cash. Completed sale, credit, cash, stock, audit, and outbox rows commit atomically.
6. **Zero-total sale:** a 100% promotion/checkout discount produces `payment_type=free`, `cash_applied=0`, `credit_amount=0`, `paid=0`, and `change=0`; no customer, cash drawer row, payment, or credit row is required. Stock/sale/audit/outbox still commit. A later full-sale return restores stock through the same deterministic refund graph with zero money effects.
7. **Hold/Cancel:** a hold is a durable synced shop draft, not a completed sale, and has no stock reservation or stock/cash/credit/COGS/report effect. It is visible shop-wide but may be resumed/cancelled offline only on its origin device by an active user with `sale_entry`; other devices are read-only in B2. Holds do not expire automatically. Resume always refreshes/revalidates. Cancel only terminates a current/held draft and never cancels a completed sale.
8. **Prescription:** checkout can capture prescription number, patient name, and prescriber name as optional sale metadata. A cart containing `requires_prescription` medicine shows a warning/prompt but metadata/image absence does not block sale. Before sale commit, a selected camera image is copied from its temporary URI into durable app-owned storage and referenced locally. Resumable Storage upload/sync occurs after commit; confirmed upload removes only retry/temp metadata, never the durable sale attachment record.
9. **Full-sale refund:** one refund covers every immutable sale item and its exact net paid amount; partial item/quantity return is outside B2. Eligibility is inclusive through `sale_business_date + max_refund_days` using Asia/Dhaka dates. Required reason is non-empty text. Return posts on the current open business day, restores quantities to original batches, marks history by relation, and leaves the original sale/day immutable. Refund initiation is the narrow online-only exception: the UI reads SQLite, but only `sync/` may request the server claim before any local refund effect.
10. **Refund payment reversal:** reverse the sale’s exact recorded cash and credit components. Any still-outstanding sale credit is canceled; any later collection allocated to that sale credit is refunded by its recorded method. Only cash components reduce expected drawer cash. Historical payments are deterministically FIFO-allocated by customer, timestamp, and ID; any residue/hash mismatch blocks refunds for the affected customer/sales until audited reconciliation succeeds.
11. **Refund authority and idempotency:** derive one operation ID from shop+sale and deterministic child IDs from operation+effect/sale-item. An authenticated, same-shop `sale_return` server RPC atomically claims that sale for the operation, actor, and device only if no other active or committed refund authority exists. The server persists the claim before replying; same-operation/same-device retries return the same claim and conflicting claims reject. A claim remains authoritative until its refund operation commits server-side; it never expires or reassigns automatically, because the server cannot prove whether physical payout occurred after claim response. After app/network failure, only the bound operation/device may resume. The local transaction must present the matching persisted claim ID/token and then commit header, return lines, payment/credit reversals, stock movements, audit, and outbox rows atomically. Offline, claim failure, timeout, or conflict leaves sale, stock, cash, credit, and ledger unchanged; the action is disabled with “Internet required for refund.” Any exceptional abandoned-device recovery requires a separately approved audited server reconciliation, not automatic B2 release.
12. **Low stock:** shop setting is a live fallback of 10. A nullable medicine override wins; every existing threshold is migrated as an explicit override. New medicines default to no override. Changing the shop fallback never bulk-rewrites medicines.
13. **Expiry bands:** Expired is `< 0` days, Near is `0–30`, Far is `31–60`, and later/null batches are outside expiry alerts. Values are shared by inventory, expiry, notifications, and promotion eligibility; validated settings require non-negative integer Near `<` Far.
14. **Barcode:** barcodes are not unique within a shop. More than one active exact match always opens an ambiguity picker. A sole sellable match may auto-select; deleted, expired-only, or no-sellable-stock matches never auto-add.
15. **Archive/oversell reconciliation:** medicine/batch archive is a soft state transition allowed only at zero ledger-derived stock, null `oversold_at`, and no active promotion. Medicine validation covers every child batch. Archive preserves children, receipt snapshots, sale items, movements, promotion history, and audit. A valid late synced movement is always applied; if it makes an archive invalid, atomically reactivate the batch/medicine and flag audited reconciliation. Refund to an archived original batch likewise reactivates it before the positive movement. `oversold_at` clears only in an audited physical-count transaction whose compensating ledger adjustment leaves derived stock non-negative.
16. **CSV:** Owner-only import supports new medicines and new batches under an Owner-confirmed unique medicine match. Existing medicine+batch collisions, ambiguous matches, conflicting metadata, and duplicate file rows reject preview; import never updates an existing batch or medicine. Required columns are prototype `name`, `generic`, `manufacturer`, `batch_no`, `stock`, `purchase_price`, and `sale_price`; `type`, expiry, threshold override, barcode, and production unit are optional, with unit explicitly previewed/defaulted to `piece`. Decimal-taka text is parsed directly to integer paisa. Files are capped at 2 MiB/1,000 data rows; larger files reject before parsing. One confirmed import ID/file fingerprint, import audit, entities, opening movements, and outbox graph commit all-or-nothing.
17. **Core invariants:** completed records remain immutable; stock changes only through signed ledger movements; every money value is integer paisa; all reads are SQLite-first; all synced writes include outbox rows; all FKs declare `onDelete`; and every query/write validates same-shop identity and current permission.

## UPDATED DECISIONS

1. Expired stock is hard-blocked after its printed expiry date; null expiry is sellable and FEFO-last.
2. Each consumed batch supplies its own current effective price; checkout refreshes/revalidates and changed quotes require reconfirmation.
3. Manual discount is Checkout-only, sale-level amount or percentage, capped at the promotion-adjusted subtotal; promotions stack first.
