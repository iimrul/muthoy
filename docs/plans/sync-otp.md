# Sync Queue Writer + Minimum-Viable Sync Engine + Real Phone OTP

## In plain English

Right now the app only lives on one phone — nothing leaves the device. This build makes three things true:

1. Every sale, purchase, credit entry, etc. gets a little "needs to sync" note attached to it the moment it's saved (offline or not).
2. When the phone has internet, those notes get sent up to the cloud in small batches, automatically, in the background — never blocking a sale. If sending fails (bad signal), it quietly retries with increasing delays.
3. Registration now asks for a real SMS code (OTP) to verify the owner's phone number, instead of just trusting whatever phone number is typed in. This also lets the cloud know which shop's data belongs to which device, securely — and it doubles as the "I already have a shop, this is just a new phone" check, so reinstalling the app or switching phones restores the real shop instead of quietly creating a second empty one.

For Beta, if the same row is somehow edited on two devices before either syncs (shouldn't happen — each shop uses one phone during the pilot), **whichever edit happened most recently just wins**, including for stock counts. The smarter merge logic (so nothing is silently lost in that rare case) is already planned as the very next piece of work after Beta, before this ever goes to a shop with more than one device.

## ⚠ Round 10 security + correctness audit of the LIVE implementation — confirmed critical findings

Full read of the actual live code (not this document) — `backend/supabase/migrations/20260813000000_initial_schema.sql`, `backend/supabase/functions/sync/**`, `apps/mobile/db/sync-helpers.ts`, `apps/mobile/sync/**`, `apps/mobile/app/(auth)/{otp-verify,register,pin-setup}.tsx`, `apps/mobile/db/auth.ts`, `apps/mobile/app/index.tsx`, `apps/mobile/db/schema.ts`. Round 8's finding stands confirmed and is now further characterized: the live implementation is real, substantial, and in several places (hydration ordering, LWW, `audit_logs` append-only, insert/update payload completeness, delete-payload ownership) it already correctly matches this document's rounds 1-9 designs. But five gaps are **confirmed, live, exploitable** issues, not theoretical:

**CRITICAL 1 — Cross-tenant row hijack via push.** `sync_apply_row`'s upsert branch (verbatim, one per table): `insert into medicines ... on conflict(id) do update set (...) = (excluded....) where medicines.updated_at < excluded.updated_at` — **no `shop_id` predicate at all**. The Edge Function's `authorizeRow()` only checks that the incoming `payload.shop_id` equals the caller's own claimed shop — it never queries what shop the row *currently* belongs to. An authenticated user of shop A who learns/observes any row UUID (`medicines`, `batches`, `sales`, `customers`, `sale_items`, etc. — any of the 19 "normal" tables) belonging to shop B can push an `update` (or soft-`delete`) for that `rowId` with `payload.shop_id` set to their **own** shop A and a newer `updated_at`, and the row is silently reassigned/overwritten/deleted — a real cross-tenant takeover, not a hypothetical.

**CRITICAL 2 — link-device tenant takeover.** `linkDevice.ts`, verbatim: checks only `callerShopId(user)` (the caller's *own* current claim) — `if (existing && existing !== shopId) reject`. If `existing` is unset (any freshly OTP-verified, not-yet-linked user), there is **no check that `shopId` isn't already claimed by a different user**, no check against `shops.owner_id`, no invite token. Any unlinked authenticated phone can call `link-device` with an arbitrary UUID and permanently bind their session to an existing, unrelated shop — full read/write access to that shop's cloud data via subsequent push/pull.

**HIGH 3 — Queue ordering: same-batch dependent rows aren't held back.** Cross-*invocation* head-of-line blocking is correctly implemented (`retryNotBefore`, in-memory, truncates `listPendingSyncRows`'s seq-ordered batch at the first still-backed-off row). But *within* one already-sent batch, all rows are dispatched together before any outcome is known — a lower-seq row's failure does not stop a same-batch, higher-seq, FK-dependent row from being attempted. It currently "self-heals" only because a resulting Postgres FK violation (`23503`) happens to fall into the generic `else → transient` bucket and gets retried — this is incidental, not designed, and provides **zero protection for the polymorphic no-FK columns** (`payments.party_id`/`ref_id`), which would apply silently out of order with no error at all.

**HIGH 4 — Postgres FK existence alone permits cross-shop references.** Every FK in the schema (`batches.medicine_id`, `sale_items.sale_id`/`medicine_id`/`batch_id`, `sales.customer_id`/`staff_id`, `purchase_items.*`, `credits.*`, `cash_drawer.opened_by`/`closed_by`, `audit_logs.actor_id`, etc. — confirmed exhaustively against the live migration) only checks "does a row with this id exist," never "does it belong to the same shop as the row referencing it." A shop-A row can legitimately FK-reference a shop-B row (e.g. a sale line item pointing at another shop's batch) and Postgres will accept it.

**CRITICAL 5 — Registration crash recovery: no durable cloud-link tracking, confirmed silent-stranding path.** `createShopAndOwner` writes `shops`/`roles`/`users` locally (queuing `sync_queue` inserts unconditionally) with **no column anywhere recording cloud-link status** — confirmed absent from the live `shops` schema. The only guard against a duplicate `createShopAndOwner` call is `otp-verify.tsx`'s in-memory `pendingShopIdRef`, which does not survive an app kill. Traced end-to-end: a crash/kill between `createShopAndOwner` succeeding and `linkDeviceToShop` failing/never-running leaves `pinSetAt` still `NULL` → next launch's `RootSessionGate` → `getRegistrationStatus()` returns `'incomplete'` → routes straight to `/(auth)/pin-setup`, **never back to OTP/link**. Once PIN setup completes, `getRegistrationStatus()` returns `'complete'` and `RootSessionGate` never again checks Supabase link state — the shop runs indefinitely with a fully-populated `sync_queue` that can never successfully push (unlinked session), no cloud backup, and no user-visible signal that anything is wrong.

**Confirmed correct, no fix needed:** RLS policies (correctly scoped for the direct-PostgREST path — explicitly not relied on for the sync/RPC path, by design); `REVOKE`/`GRANT` on both RPCs (`service_role`-only, correctly locked down); `audit_logs` append-only (both server `MU001`+`DO NOTHING` and client `onConflictDoNothing`); insert/update payload completeness (`recordChange` re-reads the full row); delete-payload ownership fields; LWW strict-`<`/tie-favors-local semantics (client and server); full-hydration two-phase stage-then-apply via `HYDRATION_TABLE_ORDER` (round 9's design — already live); `linkDeviceToShop`'s link-then-refresh-then-verify-claim sequencing (round 1's design — already live). One minor robustness note, not a security issue: `retryNotBefore`/backoff-eligibility is in-memory-only (resets on app restart; the `attempts` cap itself is durable in SQLite and still bounds total retries).

## Design

### 1. Postgres schema & RLS — `backend/supabase/migrations/`

One new migration (Supabase CLI timestamp-prefixed, e.g. `<timestamp>_initial_schema.sql` — mirrors the SQLite precedent of one large initial migration, `0000_open_senator_kelly.sql`).

**21 tables, not 24.** Start from the 24 SQLite tables and exclude three, each for a stated reason:
- `sync_queue`, `conflict_queue` — local-only outbox/staging *mechanics* for one device's write buffer. Postgres doesn't need "a queue of things to push back to SQLite" — pull is served by ordinary `updated_at`-filtered reads against the real business tables.
- `notifications` — already decided device-local and excluded from the sync outbox entirely (`isDirty: false` hardcoded in `notifications.ts`; DECISIONS.md: "excluded from the sync outbox"). Nothing will ever enqueue a row for it, so a Postgres mirror would be permanently empty — same reasoning as the other two, just applying it to a table that isn't itself outbox machinery.

Remaining 21: `shops, subscriptions, roles, permissions, users, medicines, batches, inventory_movements, customers, sales, sale_items, sales_returns, suppliers, purchases, purchase_items, purchase_returns, credits, expenses, payments, cash_drawer, audit_logs`. Tables with no live SQLite write-path yet (`subscriptions`, `permissions`, `sales_returns`, `purchase_returns`) are still created now — Volume 0's own Day-12 checklist requires RLS to be verified on every table, and standing each one up now avoids a second migration when a P1 feature eventually writes to it.

**Column-shape decisions (per-dialect, not byte-for-byte mirroring):**
- `id` and every FK: Postgres native `uuid`, not `text`. SQLite's `text` was a SQLite limitation (no native UUID type), not a design intent worth preserving — every id is already a valid UUID (`expo-crypto`'s `randomUUID()`), so there's no conversion risk.
- Money: `bigint` (paisa) — hard precondition already logged in DECISIONS.md; a `numeric`/float mismatch would silently corrupt every synced amount by 100x. (23 money columns total — cross-checked against DECISIONS.md's own count while enumerating the schema.) `sale_items.discount_value` stays `double precision` — it's a discount *rate*, not a money amount, mirroring SQLite's `real`.
- `is_dirty` is **dropped** — Volume 3 itself annotates it "(SQLite side)"; it has no meaning on the table that *is* the sync target. Every other `base` column carries over: `created_at`, `updated_at` (`timestamptz not null default now()`), `is_deleted`, `deleted_at`, `deleted_by`.
- `shop_id` gets a plain btree index on every table that has one — RLS filters on it constantly.

**RLS policy pattern**, per table with a direct `shop_id` column:
```sql
alter table medicines enable row level security;
create policy shop_isolation on medicines for all
  using (shop_id = (auth.jwt() -> 'app_metadata' ->> 'shop_id')::uuid)
  with check (shop_id = (auth.jwt() -> 'app_metadata' ->> 'shop_id')::uuid);
```
`app_metadata` (never `user_metadata`) because it's service-role-settable only — a client can never forge its own `shop_id` claim. Refines Volume 3's shorthand `auth.jwt() ->> 'shop_id'` to the correct claim path — flagged as a deliberate deviation from the doc's literal wording (rule 11), not a formatting nit.

`shops` itself is special-cased (`using (id = (auth.jwt() -> 'app_metadata' ->> 'shop_id')::uuid)` — no `shop_id` column of its own). **`permissions` breaks the uniform pattern entirely** — it has no `shop_id` column at all, only `role_id → roles.id`. Its policy has to join through `roles`:
```sql
create policy shop_isolation on permissions for all
  using (role_id in (select id from roles where shop_id = (auth.jwt() -> 'app_metadata' ->> 'shop_id')::uuid));
```
`audit_logs` gets insert + select policies only — no update/delete policy at all, enforcing append-only at the database level, matching the SQLite side.

**Why RLS matters even though the Edge Function itself uses the service-role key (which bypasses RLS) — three independent enforcement layers, not one (Codex's RPC-privilege finding below is what makes it three, not two):**
1. RLS protects the **direct PostgREST table path**. The mobile app ships a public anon key (extractable from any built APK); once a real user has a valid, OTP-verified session, nothing stops a modified client from calling `https://<project>.supabase.co/rest/v1/sales?select=*` directly with their own JWT. Without RLS, that returns every shop's sales. This is exactly what Volume 0's own Day-12 checklist tests: "using shop A's credentials, attempt to read/write a row belonging to shop B directly."
2. The Edge Function's own manual `app_metadata.shop_id`/`rowId`/`payload.id`/role-join checks (§2) protect the **service-role path**, which RLS cannot touch by definition.
3. **Explicit `REVOKE`/`GRANT` on `sync_apply_row` and `sync_pull_changes` themselves** protects a **third, previously-unguarded path: calling the RPC functions directly** (`/rest/v1/rpc/sync_apply_row`) with nothing but the extractable anon key. Both functions are `SECURITY DEFINER` *by design* — that's what lets them bypass RLS when legitimately called from the Edge Function — but Postgres grants `EXECUTE` on newly created functions to `PUBLIC` by default. Left unrevoked, that default would let any client call either function directly, fully bypassing every check in layer 2 (the Edge Function never runs at all on this path) — and RLS (layer 1) doesn't apply here either, since an RPC call runs as the function's owner, not through the underlying tables' policies. Layer 3 is the only thing that closes this path; it's not redundant with 1 or 2, it protects a path they structurally cannot reach. Fix: immediately after each `CREATE FUNCTION`, in the same migration —
   ```sql
   revoke execute on function sync_apply_row(text, text, jsonb) from public, anon, authenticated;
   grant execute on function sync_apply_row(text, text, jsonb) to service_role;

   revoke execute on function sync_pull_changes(uuid, timestamptz, text, uuid, int) from public, anon, authenticated;
   grant execute on function sync_pull_changes(uuid, timestamptz, text, uuid, int) to service_role;
   ```
   Confirmed compatible with the Edge Function push/pull flow: `supabaseAdmin` (§2's `_shared/supabaseAdmin.ts`) calls both via `.rpc()` authenticated as `service_role`, which keeps `EXECUTE` — nothing in §2 changes. Only a direct anon/authenticated caller loses access, which is the entire point.

**The actual upsert/LWW mechanism is two Postgres functions, defined in this same migration** — not ad hoc queries built in Deno:
- `sync_apply_row(p_table text, p_op text, p_row jsonb) returns text`, `security definer`. Deliberately **explicit per-table branches**, not a generic dynamic-SQL dispatcher — a `format()`+`EXECUTE`-built statement would need to interpolate a client-influenced string into a SQL identifier position to be generic, which is an injection-adjacent risk explicit branches make structurally impossible. **Because every `insert` and `update` payload is now guaranteed complete-row (see §3's outbox-payload fix), `insert` and `update` share one code path per table**: `INSERT ... ON CONFLICT (id) DO UPDATE SET <every column> = excluded.<column> ... WHERE <table>.updated_at < excluded.updated_at`. No per-op branching inside a table's SQL block any more — `p_op` only selects between this unified upsert path and the separate soft-delete path (`UPDATE ... SET is_deleted = true, deleted_at = ..., deleted_by = ...`, same LWW guard). Rejects any `p_table` not on a hardcoded allowlist. *(Simplification note: the original design had insert/update as textually-identical-but-separate branches per table; collapsing them is a direct consequence of the payload-completeness fix, not a separate change.)*

**`audit_logs` is the one table that keeps its own distinct branch, not the unified upsert (Codex-flagged).** `audit_logs` already has insert+select-only RLS policies (append-only, no update/delete policy exists at all) — but `sync_apply_row` is `SECURITY DEFINER` and bypasses RLS by design, so without an explicit guard *inside the function itself*, the now-unified insert/update branch would let a client push an `update` op targeting an existing `audit_logs` row's id and silently rewrite audit history through the service-role path, defeating the append-only guarantee RLS enforces everywhere else. Its branch:
```sql
when p_table = 'audit_logs' then
  if p_op = 'insert' then
    insert into audit_logs (...) values (...)
    on conflict (id) do nothing;  -- retried/duplicate push of the same row is a harmless no-op; never touches existing columns
  else
    raise exception 'audit_logs is append-only; op % is not permitted', p_op
      using errcode = 'MU001';    -- custom SQLSTATE, distinguishable from 23505 by the Edge Function
  end if;
```
`ON CONFLICT (id) DO NOTHING` (not `DO UPDATE`) means an existing-id conflict — e.g. a retried push of a row already applied — is always a no-op against the *existing* row, never a modification, satisfying "existing-ID conflict must never modify existing audit history" exactly. `update`/`delete` ops raise immediately, before touching the table at all; this is defense-in-depth against a tampered client, not a real operational path — nothing in this design's local write sites (§3's retrofit table) ever issues anything but `op: 'insert'` for `audit_logs`, matching DEVELOPMENT_RULES' append-only rule for audit logs on the SQLite side too.

The Edge Function (§2) maps SQLSTATE `MU001` the same way it already maps `23505` — straight to `reason: 'permanent'`, never `'transient'`, so a rejected illegal audit-log mutation is surfaced once (stuck-sync notification) and never endlessly retried through the 8-attempt backoff.

**`audit_logs` is untouched by the round-4 delete-ownership fix, by construction.** `buildDeletePayload()` above is keyed on `SyncTableName`'s three ownership categories (normal / `shops` / `permissions`); `audit_logs` never reaches it or needs a category of its own, because `sync_apply_row`'s `audit_logs` branch already rejects `op: 'delete'` outright (SQLSTATE `MU001`) before any authorization check would even run — and no local call site issues a delete for it in the first place. Append-only holds exactly as already established; this round adds nothing new here, only confirms no exception was introduced.

**Round 10 CRITICAL FIX 1 — `sync_apply_row` must verify the EXISTING row's shop before mutating it, not just trust the incoming payload.** The live function's upsert/delete branches guard only on `updated_at`, never `shop_id` — payload-declared ownership was being treated as if it authorized a mutation of *any* row by that id, which it must never do. Fix: **every branch's `WHERE` clause gets an added ownership predicate against the existing row**, and `sync_apply_row` gains a new parameter, `p_caller_shop_id uuid` (passed by the Edge Function from the already-verified JWT claim — the same value `authorizeRow()` already computes, just now also handed to the RPC instead of trusted to have done its job upstream):
```sql
-- upsert (insert/update unified branch), per table, e.g. medicines:
insert into medicines select * from jsonb_populate_record(null::medicines, p_row)
  on conflict(id) do update set (...) = (excluded....)
  where medicines.shop_id = p_caller_shop_id and medicines.updated_at < excluded.updated_at;
-- soft-delete, per table:
update medicines set is_deleted=true, deleted_at=..., deleted_by=..., updated_at=...
  where id = (p_row->>'id')::uuid and shop_id = p_caller_shop_id and updated_at < (p_row->>'updated_at')::timestamptz;
```
For a genuinely new row (no existing conflict), `medicines.shop_id = p_caller_shop_id` never gets evaluated against an existing row (the `INSERT` branch of `ON CONFLICT` fires instead) — so this adds zero friction for legitimate inserts under one's own shop. For an UPDATE/soft-delete targeting a row that already exists but belongs to a *different* shop, the `WHERE` clause is now false regardless of what the payload claims — the statement matches zero rows, and `sync_apply_row` returns a distinct outcome (`'rejected_not_owned'`, mapped by the Edge Function to a `permanent` push rejection, not silently reported as `'applied'`) so the client sees a real, actionable rejection rather than a silent no-op it can't distinguish from a stale-LWW no-op. `shops` and `permissions` get the equivalent predicate in their own terms (`shops.id = p_caller_shop_id`; `permissions`' branch already resolves its owning shop via the `roles` join for authorization — round 10 extends that same join into the `WHERE` clause itself, `where exists (select 1 from roles r where r.id = permissions.role_id and r.shop_id = p_caller_shop_id)`, rather than trusting the pre-check alone). `audit_logs` is unaffected (already insert-only, already rejects update/delete outright, per-row ownership was never its gap).

**Round 10 HIGH FIX 4 — same-shop enforcement on every FK, not just `shop_id → shops.id`.** Postgres FK constraints verify existence only, never same-tenant-ness. Every non-root FK column in the live schema needs an explicit same-shop check before the row is applied: `batches.medicine_id→medicines`; `inventory_movements.batch_id→batches`, `.created_by→users`; `sale_items.sale_id→sales`, `.medicine_id→medicines`, `.batch_id→batches`; `sales.customer_id→customers` (nullable), `.staff_id→users`; `sales_returns.sale_id→sales`, `.sale_item_id→sale_items`, `.created_by→users`; `purchases.supplier_id→suppliers`; `purchase_items.purchase_id→purchases`, `.medicine_id→medicines`; `purchase_returns.purchase_id→purchases`, `.purchase_item_id→purchase_items`, `.created_by→users`; `credits.customer_id→customers`, `.sale_id→sales` (nullable); `expenses.created_by→users`; `payments.created_by→users`; `cash_drawer.opened_by→users`, `.closed_by→users` (nullable); `audit_logs.actor_id→users`; `users.role_id→roles`; `roles`/`subscriptions`/`medicines`/`customers`/`suppliers` already covered by their own direct `shop_id` check. **Mechanism (smallest robust option, consistent with `sync_apply_row`'s existing "explicit branches, never dynamic SQL" philosophy):** one small shared helper, `assert_fk_same_shop(p_ref_table text, p_ref_id uuid, p_shop_id uuid)` — itself a small, hardcoded-allowlist `if/elsif` (same injection-safety reasoning as `sync_apply_row` itself), returning boolean — called once per relevant FK column inside each table's branch, before the upsert executes; `raise exception ... using errcode = 'MU003'` on failure (nullable FK columns skip the check when the value is null). `MU003` is mapped by the Edge Function the same way as `MU001`/`23505`/the new "not owned" outcome — straight to `permanent`, never retried (a cross-shop reference is never going to become valid by waiting). **Note on `payments.party_id`/`ref_id`**: these are polymorphic, no-FK-at-all columns (existing design) — `assert_fk_same_shop` can't help them since there's no fixed target table; they remain an accepted gap unless/until a discriminator column (`party_type`) is added to make the lookup well-defined — flagged explicitly, not silently left unaddressed.
- `sync_pull_changes(p_shop_id uuid, p_since_updated_at timestamptz, p_since_table text, p_since_id uuid, p_limit int) returns table(table_name text, row_id uuid, updated_at timestamptz, row_data jsonb)`, `security definer`. **Composite cursor, resolved per the pagination fix below.** Body:
  ```sql
  with all_changes as (
    select 'medicines'::text as table_name, id as row_id, updated_at, to_jsonb(t.*) as row_data
      from medicines t where t.shop_id = p_shop_id
    union all
    select 'batches', id, updated_at, to_jsonb(t.*) from batches t where t.shop_id = p_shop_id
    union all
    -- ... one branch per remaining normal table (19 total), same `shop_id = p_shop_id` shape
    union all
    select 'shops', id, updated_at, to_jsonb(t.*) from shops t where t.id = p_shop_id
    union all
    select 'permissions', id, updated_at, to_jsonb(t.*) from permissions t
      where t.role_id in (select id from roles where shop_id = p_shop_id)
  )
  select table_name, row_id, updated_at, row_data
  from all_changes
  where p_since_updated_at is null
     or (updated_at, table_name, row_id) > (p_since_updated_at, p_since_table, p_since_id)
  order by updated_at, table_name, row_id
  limit p_limit
  ```
  The `shops` and `permissions` branches use the exact same predicate shape as their RLS policies (§1, above) and as push's per-row authorization (§2) — one authorization rule per table, defined once, applied identically across RLS, push, and pull.

  **Round 9: reverts round 7's `table_rank`-primary ordering entirely — round 7 fixed full hydration by breaking the durable incremental cursor.** `table_rank` is a fixed, static per-table attribute — it does not increase over time the way `updated_at` does. Once a device's persisted cursor advanced past a high-ranked table it happened to see in one sync cycle (say `audit_logs`, rank 20), any *future* write to a lower-ranked table (say `medicines`, rank 5) would produce a tuple `(5, <new updated_at>, id)` that sorts *below* the stored `(20, ...)` cursor — the strict `>` filter would silently and **permanently** exclude that row from every subsequent incremental pull. A durable watermark must be monotonic in a dimension that only moves forward in real time; `table_rank` isn't that dimension, `updated_at` is. This function reverts to exactly round 3's shape — ordered/filtered purely by `(updated_at, table_name, row_id)`, no table awareness at all, identical behavior for full hydration (`since: null`) and ordinary incremental pulls. It stays the tie-free, lossless, resumable cursor round 3 established (requirement 3, preserved). **FK-safe apply order is no longer this function's job at all — see §4 for where it now lives, client-side, hydration-only.**

**No generic `set_updated_at()` trigger is attached to any of these 21 tables.** Volume 3 specifies exactly this trigger, blanket-applied to mutable tables. Applying it here would silently overwrite the client's true edit timestamp with server arrival time on every upsert — corrupting the exact field LWW compares on. `sync_apply_row` sets `updated_at` explicitly from `p_row->>'updated_at'` (the trusted client payload), never `now()`. Deliberately omitted from this migration; logged as a DECISIONS.md carve-out (§9) so a future contributor doesn't "fix" this by adding the trigger back. There's also no legitimate use case for it yet — the only write path into Postgres is this sync function; the P0 Basic Admin Panel is read-only aggregate, no direct-edit path exists.

### 2. Edge Function — `backend/supabase/functions/sync/`

One function (matching the docs' "exactly two Edge Functions total" framing — sync + the P1 payment webhook), split into files rather than one flat script:
```
sync/index.ts              — entrypoint, routes on `action`
sync/push.ts
sync/pull.ts
sync/linkDevice.ts
sync/_shared/supabaseAdmin.ts  — one service-role client, module-scoped
sync/_shared/auth.ts           — verifyCallerJwt() + shop_id-match guard, shared by all 3 routes
sync/_shared/tables.ts         — SYNCED_TABLES allowlist (deliberately duplicated from the mobile-side registry — Deno can't cleanly consume a pnpm-workspace-local package, so this is a small, commented, cross-referenced duplication rather than a build-time dependency). Also exports the 3-way authorization category used by push.ts's per-row check (§2): normal (`shop_id` column), `'shops'`, `'permissions'` — one table, `'shops'`/`'permissions'`, never falls into the generic branch by accident.
```
`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are auto-injected into every Edge Function's environment by Supabase — no manual secret setup for those two specifically.

**Auth, uniform across all three actions:** every request carries `Authorization: Bearer <token>` (the phone-verified session held by `sync/supabaseClient.ts`). `_shared/auth.ts` calls `supabaseAdmin.auth.getUser(token)` to verify signature+expiry and read `app_metadata.shop_id`. Push/pull additionally require the body's `shopId` to equal that claim exactly (403 on mismatch, not 500) — the manual check standing in for RLS on the service-role path.

- **`action: 'link-device'`** — `{ shopId }` → `supabaseAdmin.auth.admin.updateUserById(user.id, { app_metadata: { shop_id: shopId } })` (the *only* way to set `app_metadata` — client-side `updateUser()` can only touch `user_metadata`, which is exactly why this must be a server call, not something `sync/` does directly). Idempotent if already linked to the same shop; **rejected (403) if already linked to a different one** — a compromised client shouldn't be able to hop identities by repeated calls.

  **Round 10 CRITICAL FIX 2 — this was never enough.** The live implementation checks only the *caller's own* current claim (`existing`) — nothing stops an unlinked authenticated user from calling `link-device` with an **arbitrary** `shopId` belonging to a completely different, already-established shop, permanently binding their session to it (full subsequent read/write via push/pull, since RLS and the Edge Function both key entirely off `app_metadata.shop_id`). The original "shop ids are cryptographically random UUIDs, nothing to guess" reasoning only covers the *brand-new* case (a shop THIS session just created) — it says nothing about a *different*, pre-existing shop's id being supplied instead, whether guessed, leaked, or supplied by a user who simply has no legitimate relationship to that shop.

  **Fix: first-claim-wins, enforced by a small dedicated Postgres table, not by `app_metadata` inspection alone.**

  **Round 11 correction — `shop_claims.shop_id` must NOT FK to `shops(id)`.** The real registration order is: local SQLite shop creation → `link-device` claims `shopId` → `refreshSession()` → the `shops` row itself only reaches Postgres later, via the *first async push* (it's queued through the ordinary `recordChange`/`sync_queue` path like any other row, per `createShopAndOwner`). At the moment `link-device` claims the id, no `shops` row exists in Postgres yet — a FK would make every legitimate claim fail with a foreign-key violation. `shop_claims` is therefore an **independent ownership registry, deliberately decoupled from `shops`'s own existence**:
  ```sql
  create table shop_claims (
    shop_id uuid primary key,                          -- no `references shops(id)` — claimed before the row exists
    claimed_by_user_id uuid not null unique,            -- one Supabase account claims at most one shop, ever
    claimed_at timestamptz not null default now()
  );
  alter table shop_claims enable row level security;    -- zero policies: RLS-enabled + no policy = zero rows visible
                                                          -- to anon/authenticated via PostgREST; service_role bypasses
                                                          -- RLS entirely, which is the only way this table is ever touched.
  ```
  `claimed_by_user_id unique` is a DB-level backstop (defense in depth, not the primary gate — see below) enforcing "one account, one shop, ever," matching Beta's single-owner-per-shop model.

  `link-device`'s handler:
  ```ts
  const existing = callerShopId(user);
  if (existing && existing !== shopId) throw new HttpError(403, 'User is already linked to another shop');
  if (!existing) {
    const { data: claim } = await supabaseAdmin
      .from('shop_claims')
      .insert({ shop_id: shopId, claimed_by_user_id: user.id })
      .select()
      .maybeSingle(); // conflict on the shop_id PK is swallowed by an explicit onConflict('shop_id').ignore()
    if (!claim) {
      const { data: existingClaim } = await supabaseAdmin.from('shop_claims').select('claimed_by_user_id').eq('shop_id', shopId).single();
      if (existingClaim?.claimed_by_user_id !== user.id) throw new HttpError(403, 'Shop already linked to a different account');
      // else: idempotent re-link by the same user who already holds this claim — fall through
    }
    await supabaseAdmin.auth.admin.updateUserById(user.id, { app_metadata: { ...user.app_metadata, shop_id: shopId } });
  }
  ```
  (The pre-existing top-of-function `existing`/`callerShopId(user)` check — unchanged from round 10 — is the *primary* gate against one account claiming a second shop; `claimed_by_user_id unique` only matters as a backstop if that check is ever bypassed or races.) First call for any given `shopId` wins the claim atomically; every subsequent call from a *different* user is rejected regardless of the caller's own `app_metadata.shop_id` state. No invite-token system needed — "who's allowed to claim shop X" is answered structurally (whoever's device generated the unguessable UUID and links first, wins).

  **Verification against the four named areas:**
  - **RLS**: `shop_claims` gets RLS enabled with **zero policies** — the safest posture for a table only the service role should ever touch (round 10's original note that "RLS isn't needed" was itself an oversight this round corrects: without RLS, Supabase's default grants could make the table readable via PostgREST by any authenticated user, leaking the shop_id→user_id map). `shops` and the other 20 business tables' RLS policies are unaffected — this is a new, separate table.
  - **`sync_apply_row`**: no direct interaction, and none is added. The authorization chain is layered, not merged: `shop_claims` (link-device) sets the JWT's `app_metadata.shop_id` → the Edge Function's `authorizeRow` checks a push payload against that JWT claim (for `shops` rows: `payload.id === callerShopId`) → `sync_apply_row`'s own ownership `WHERE` clause (round 10 fix 1) guards *updates* to an already-existing row. The very first `shops`-row insert (which is what actually creates the row in Postgres) is authorized entirely by the Edge-Function-level check, since `sync_apply_row`'s ownership `WHERE` clause only applies to the `ON CONFLICT` update path, not a fresh insert — consistent and requires no change. **This is also the answer to "later cloud shops insert must match the caller's claimed shop_id"**: `payload.id === callerShopId` already enforces it, and `callerShopId` can only ever equal a value that was legitimately set by a successful `shop_claims` insert — there's no separate check to add.
  - **Existing-shop hydration**: the restore branch never calls `link-device` or touches `shop_claims` directly — it trusts `session.user.app_metadata.shop_id` as read off the JWT. This is safe **by construction, not by a redundant re-check**: `app_metadata` can only be set server-side, and the only code path that ever calls `updateUserById` to set `shop_id` is `link-device`'s handler, which is now gated by the atomic claim. So "hydration checks the same claim" transitively, through the JWT, rather than by querying `shop_claims` a second time at pull time (which would be redundant work for no additional safety).
  - **Registration crash recovery (round 10 fix 5)**: fully compatible, no changes needed. If a crash happens *after* a successful claim but before `refreshSession`/later steps complete, the resume-link flow's retry of `link-device(resumeShopId)` hits the idempotent same-user branch (`existingClaim.claimed_by_user_id === user.id`) and proceeds. If the crash happens *before* `link-device` was ever called, the resume attempt is a genuine first-time claim. No partial/ambiguous state is possible either way, since the claim is one atomic `INSERT`.
- **`action: 'push'`** — `{ shopId, rows: [{ queueId, tableName, rowId, op, payload }] }` → `{ results: [{ queueId, status: 'applied' } | { queueId, status: 'rejected', reason: 'permanent'|'transient', error }] }`. Rows processed **sequentially, not in parallel** — avoids same-table write contention; batching exists to save the mobile-data hop, not because the Edge-Function→Postgres hops need it. **Per-row checks, in order, structural then shop-authorization (Codex-flagged, now made explicit per table) — identical for every `op`, `insert`/`update`/`delete` alike. There is no separate, weaker check path for deletes**: rule 2 already worked for delete unchanged (a delete payload's `id` was always present as a delete marker); rule 3 is the one that needed the delete-payload contract fix in §3 above, since the original minimal delete payload had no `shop_id`/`role_id`/`id`-as-shop to check against — it does now.
  1. `tableName` must be on the allowlist → else permanent reject.
  2. `rowId === payload.id` → else permanent reject. Uniform across every table — a mismatch means a malformed or tampered row, never a legitimate client state.
  3. Table-specific shop-authorization — mirrors §1's RLS policies exactly, table-for-table, so the service-role path (this check) and the direct-PostgREST path (RLS) enforce the identical rule per table, never two independent definitions of "who owns this row":
     - **19 normal shop-scoped tables** (everything except `shops`/`permissions`): `payload.shop_id === callerShopId` → else permanent reject (defense in depth against one tampered row, even though the outer `shopId` already matched).
     - **`shops`**: no `shop_id` column — the row *is* the shop. Check `payload.id === callerShopId` → else permanent reject. A device can only ever push its own shop's row, never create or touch another shop's. (Correctly sequenced for a brand-new registration too: `link-device` sets `app_metadata.shop_id` to the new shop's own id and `refreshSession()` completes, per §5, *before* any push can fire — so `callerShopId` already equals the new shop's id by the time its first `shops` row is pushed.)
     - **`permissions`**: no `shop_id` column and no id-based shortcut. `payload.role_id` must resolve to a role owned by the caller's shop — checked with one `select shop_id from roles where id = payload.role_id` query, run **per-row, immediately before that specific row's `sync_apply_row` call** (never once upfront for the whole batch) → permanent reject if that role's `shop_id !== callerShopId` or the role doesn't exist (yet). **Per-row timing is load-bearing, not stylistic**: rows are already applied sequentially in `seq` order, so a `roles` row created earlier in the same push batch has already committed to Postgres by the time a dependent `permissions` row (naturally sequenced after it, by real write order) is checked. A once-per-batch upfront version of this same query would race that same-batch `roles` insert and wrongly reject a correctly-ordered row — this is the FK-ordering conflict this design must avoid, not a hypothetical.
  4. Otherwise call `sync_apply_row` via `.rpc()`.

  Postgres error `23505` (unique_violation — the secondary-uniqueness collision case, see Risks), `MU001` (illegal `audit_logs` update/delete, see §1), `MU002` (unsupported op), or `MU003` (cross-shop FK reference, round 10 fix 4) → `reason: 'permanent'`; a `'rejected_not_owned'` RPC result (round 10 fix 1 — existing row belongs to a different shop) → also `reason: 'permanent'`; anything else (timeout, 5xx) → `reason: 'transient'`.

  **Round 10 HIGH FIX 3 — process the batch sequentially and stop at the first failure, don't attempt every row regardless of an earlier one's outcome.** The live handler currently dispatches every row in a batch without regard to earlier rows' results — a lower-seq row's failure doesn't stop a same-batch, higher-seq, FK-dependent row from also being attempted. It happens to mostly self-correct today only because a resulting Postgres FK violation (`23503`) falls into the generic transient bucket and gets retried — incidental, not designed, and it provides **no** protection for the two no-FK polymorphic columns (`payments.party_id`/`ref_id`), which would apply out of order with no error raised at all. Fix: the handler processes `rows` **strictly in the order received** (already seq-ordered by the client) and **stops calling `sync_apply_row` for the rest of the batch the moment one row's result is not `'applied'`** (whether rejected-transient, rejected-permanent, or rejected-not-owned) — every row after that point in the same request gets a new result status, `status: 'skipped'`, without ever reaching Postgres. The client (`push.ts`) treats `'skipped'` exactly like `'transient'`: reschedule via the existing backoff/`retryNotBefore` mechanism, don't mark sent, don't mark permanently failed. This makes "don't attempt a dependent row until its predecessor has actually succeeded" a structural guarantee of the request itself, not an emergent property of how Postgres happens to classify a downstream error — and it closes the polymorphic-column gap completely, since those rows are never attempted at all once an earlier row in the same batch has failed, regardless of whether the DB layer would have caught the problem.

  **Secondary robustness note, not required to close the security findings but worth doing alongside:** `push.ts`'s `retryNotBefore` (next-eligible-retry-time) is in-memory-only and resets on app restart — the `attempts` cap itself is durable (SQLite `syncQueue.attempts`), so total retries stay bounded at 8, but a restart can cause a burst of premature re-attempts against a row that's still genuinely backed off, spending attempts faster than the backoff schedule intends. Smallest fix: persist the computed next-eligible-time as a new nullable `syncQueue.nextAttemptAt` column (set alongside `attempts`/`lastError` on every transient failure), and have `listPendingSyncRows` filter on it directly (`nextAttemptAt is null or nextAttemptAt <= now()`) instead of relying on an in-memory map — removes the restart-reset behavior entirely.
- **`action: 'pull'`** — `{ shopId, since: { updatedAt: string; tableName: string; rowId: string } | null }` → `{ changes: [{ tableName, rowId, updatedAt, payload }], hasMore, nextCursor: { updatedAt, tableName, rowId } | null }`. **Pagination-safety fix (composite cursor, resolving the "ties across a page boundary" issue):** `since`/`nextCursor` is the full `(updatedAt, tableName, rowId)` tuple, passed straight through to `sync_pull_changes`'s `p_since_updated_at`/`p_since_table`/`p_since_id` params — **not a bare timestamp**. `nextCursor` is taken directly from the **last row actually returned in this page** (never a server-`now()` capture) — this both closes the tie-at-page-boundary hole (the tuple has no ties, per §1) and removes the old design's separate "`serverTime`-vs-client-stamped-`updated_at`" clock mismatch, since cursor and compared column are now always the same kind of value. `since: null` triggers full hydration via `sync_pull_changes`'s `p_since_updated_at is null` branch. `hasMore = (returned page length === page size requested)`. When a page returns zero rows, `nextCursor` is `null` in the response and the **client must leave its stored cursor untouched** — an empty poll must never reset pull progress.

### 3. Shared SQLite write helpers — new `apps/mobile/db/sync-helpers.ts`

No shared "write + enqueue" helper exists today; two incompatible transaction-callback styles coexist (sync-style/no-await in `sales.ts`/`purchases.ts`/`customers.ts`, `async`-style elsewhere). Plain functions, callable from either style without changing the outer callback's shape:

```ts
export function stampUpdatedAt<T extends object>(values: T): T & { updatedAt: string } {
  return { ...values, updatedAt: new Date().toISOString() }; // single canonical time source — see the timestamp-format finding below
}

export function recordChange(tx: Tx, params: {
  shopId: string; table: SyncTableName; rowId: string;
  op: 'insert' | 'update' | 'delete'; payload: Record<string, unknown>; // camelCase Drizzle shape
}): void {
  // Outbox-payload-completeness fix (see below): 'update' payloads are re-read in full,
  // never trusted as whatever partial `.set()` values the caller happened to pass.
  const outgoingPayload = params.op === 'delete'
    ? buildDeletePayload(tx, params) // ownership-aware minimal payload — see below
    : tx.select().from(TABLE_REGISTRY[params.table]).where(eq(TABLE_REGISTRY[params.table].id, params.rowId)).get();
    // insert AND update: always re-read the just-written row back from SQLite, same transaction —
    // never trust the caller's pre-write values object. See the insert-completeness fix below for why
    // this now applies to insert too, not just update.
  tx.insert(syncQueue).values({
    id: generateId(), seq: nextSeq(tx), shopId: params.shopId, tableName: params.table,
    rowId: params.rowId, op: params.op,
    payload: JSON.stringify(toSnakeCasePayload(outgoingPayload)), // converted once, here — see below
    status: 'pending',
  }).run();
}

// Delete-payload ownership fix (Codex-flagged, round 4): a delete payload with ONLY
// { id, deletedAt, deletedBy, updatedAt } — the original design — has nothing for push
// authorization (§2) to check against callerShopId, since insert/update's ownership check
// reads payload.shop_id / payload.id / payload.role_id, none of which a bare delete-marker
// payload carries. Every delete payload now also carries its table's ownership field,
// exactly mirroring insert/update's three categories:
function buildDeletePayload(tx: Tx, params: {
  shopId: string; table: SyncTableName; rowId: string; payload: Record<string, unknown>;
}): Record<string, unknown> {
  const markers = {
    id: params.rowId, isDeleted: true,
    deletedAt: params.payload.deletedAt, deletedBy: params.payload.deletedBy, updatedAt: params.payload.updatedAt,
  };
  if (params.table === 'shops') return markers; // id itself IS the ownership field — nothing to add
  if (params.table === 'permissions') {
    // Same-transaction LOCAL re-read (identical mechanism to the update-payload fix above) —
    // never a server-side lookup-by-id. See "why not server-side" below.
    const roleId = tx.select({ roleId: permissions.roleId })
      .from(permissions).where(eq(permissions.id, params.rowId)).get()?.roleId;
    return { ...markers, roleId };
  }
  return { ...markers, shopId: params.shopId }; // normal tables: already a recordChange param, free to include
}

export function applyRemoteRow(tx: Tx, table: SyncTableName, snakeCaseRow: Record<string, unknown>): 'applied' | 'skipped_stale' {
  const row = toCamelCaseRow(snakeCaseRow);
  const drizzleTable = TABLE_REGISTRY[table]; // same registry recordChange uses — one source of truth for every synced table's Drizzle object
  if (table === 'audit_logs') {
    // Append-only locally too — mirrors sync_apply_row's server-side branch (§1) exactly.
    // No LWW comparison: audit_logs is never updated by anyone, so "which is newer" doesn't apply.
    const result = tx.insert(drizzleTable).values(row).onConflictDoNothing({ target: drizzleTable.id }).run();
    return result.changes > 0 ? 'applied' : 'skipped_stale'; // reused as "already present, not re-applied" — not a timestamp comparison here
  }
  // Every other synced table — normal tables, `shops`, `permissions` alike. Their "special handling" is
  // entirely in pull's filter (§1) and push's authorization (§2); applyRemoteRow itself needs no per-table
  // branch for them beyond picking the right Drizzle table object, because the LWW guard below is already
  // column-name-generic (table.id / table.updatedAt resolve correctly for whichever table is passed in).
  const result = tx.insert(drizzleTable).values(row)
    .onConflictDoUpdate({
      target: drizzleTable.id,
      set: row,
      where: sql`${drizzleTable.updatedAt} < ${row.updatedAt}`, // local.updatedAt < remote.updatedAt — apply only if remote is strictly newer; a tie (e.g. this exact row pushed earlier, now pulled back) is a no-op, not an overwrite
    }).run();
  return result.changes > 0 ? 'applied' : 'skipped_stale';
}
```
Still **deliberately never calling `recordChange`** from inside `applyRemoteRow`, for either branch — see the pull-loop hazard below, unchanged from the original design.

**Stale-protection fix (Codex-flagged, round 5): the LWW guard was previously sketched once, generically, without stating it covers all 20 non-`audit_logs` synced tables — not just the one example table shown.** Made explicit above via `TABLE_REGISTRY[table]`, the same per-table Drizzle-object lookup `recordChange`'s re-read already uses (one registry, two consumers, not two separately-maintained table lists). `shops` and `permissions` need **no** additional branch here: their "special handling" already lives entirely upstream — pull's own filter (`sync_pull_changes`'s `id = p_shop_id` / role-join branches, §1) already guarantees only rows this shop is entitled to ever reach `applyRemoteRow` in the first place, so once a row arrives, the same generic `local.updatedAt < remote.updatedAt` guard is exactly correct for them too, same as any other table. `audit_logs` is the one genuine exception, and it needed fixing here specifically because the generic LWW-guarded `DO UPDATE` was never reconciled with the append-only fix added in round 5 to `sync_apply_row` — a pulled `audit_logs` row now gets `ON CONFLICT DO NOTHING` locally, mirroring the server-side branch exactly, never a timestamp-guarded overwrite (there is nothing to compare timestamps *for*, since no legitimate audit_logs update ever exists on either side).

**Compatibility check:**
- **LWW** — unaffected/strengthened: the guard's direction and semantics (`<`, strict, tie = no-op) are unchanged from the original design, now just explicitly stated to apply uniformly via the registry.
- **Full hydration** — a fresh device's first pull has no existing local rows to conflict with, so every table's branch (including `audit_logs`'s `DO NOTHING`) takes its plain-insert path; `DO NOTHING`/the LWW guard only matter for re-pulls of already-present rows (resumed pagination, a second sync cycle), where they're correctly idempotent either way.
- **Soft deletes** — unaffected: a remotely soft-deleted row is just a normal row with `isDeleted: true` in its snapshot, replicated through the exact same generic upsert path as any other change (pull has no separate "delete" signal to special-case); `audit_logs` never has this case since it can never be soft-deleted (§1's `MU001` guard, round 5).
- **Insert/update/delete payload rules** — no interaction: those govern what the *push* side enqueues and how the *server* authorizes it; `applyRemoteRow` only ever consumes *pull* output (`to_jsonb(t.*)`, always a full row already), untouched by either the insert-completeness fix above or the delete-ownership fix (round 4).
- **No pull→re-enqueue loop** — still structurally guaranteed: neither branch of the code above calls `recordChange`, so there remains no code path connecting a pulled row back into `sync_queue`, regardless of which branch (`DO NOTHING` vs. LWW-guarded `DO UPDATE`) actually ran.

**Outbox insert/update-payload completeness fix.** Several real call sites in this same retrofit only ever `UPDATE` a handful of columns — `changeOwnPin`/`resetStaffPin` touch `pinHash`/`pinSetAt`/`updatedAt` only, `deactivateStaff` touches `isActive`/`updatedAt` only — so the values object available at the call site, right where `recordChange` would naively be called with it, is genuinely partial. Postgres's `sync_apply_row` needs a **complete** row for `insert`, because `INSERT ... ON CONFLICT (id) DO UPDATE` always evaluates the `INSERT`'s `VALUES` list up front (even when the conflict branch is the one that ends up firing), so any NOT NULL column missing from a partial payload would either error or (if columns were loosened to nullable to dodge that) silently null out real data in the rare case the row didn't already exist server-side. **Chosen fix — the simplest robust option: `recordChange` itself guarantees completeness, centrally, once, rather than pushing that burden onto every call site.** For `op: 'update'`, it re-reads the row from SQLite by id, in the *same transaction*, immediately after the caller's own `UPDATE` has already run — the read is guaranteed to see the caller's just-written values (same tx, no isolation gap) plus every untouched column. Call sites are unaffected: they keep writing minimal, targeted `UPDATE` statements exactly as already planned in the retrofit table below; only `recordChange`'s internals change. **`op: 'insert'` gets the identical re-read treatment (Codex-flagged, round 5) — the earlier "caller's values are already the complete just-constructed row" assumption was wrong.** `.insert(table).values(callerValues)` does not require `callerValues` to supply every column: schema-defaulted columns (`createdAt`'s `sql\`(current_timestamp)\`` default, `isDeleted`'s `false` default, nullable `deletedAt`/`deletedBy`) are legitimately omitted by real call sites and filled in by SQLite itself at write time — so the pre-write `callerValues` object is *not* guaranteed to equal the row that actually ends up persisted. Building the outbox payload from `callerValues` directly risks either omitting those DB-filled columns entirely, or (worse, and explicitly disallowed) a caller "helpfully" pre-filling a guessed `null` for one to avoid the gap — which would push an *actual* NULL for a column Postgres has as NOT NULL, since `sync_apply_row`'s `INSERT ... VALUES` reads straight from the JSONB payload with no defaulting of its own. Fix: **insert now uses the exact same post-write, same-transaction re-read as update** (the code above) — call the `INSERT`, then read the row back by `id` from the same table, same `tx`, and enqueue *that* — guaranteed byte-for-byte identical to what SQLite actually persisted, defaults and all, never a guess. This is a strict simplification, not two separate mechanisms: `recordChange` now has one rule for `insert`/`update` ("re-read what's actually there") and one rule for `delete` (`buildDeletePayload`'s ownership-aware minimal markers, unaffected by this fix — a soft-delete only ever sets a handful of marker columns, never omits a NOT NULL column that needs defaulting).

`op: 'delete'` payloads stay minimal (id + ownership field + delete markers, §3 round 4) since soft-delete is a separate, narrower SQL branch server-side that was never affected by either completeness issue. Net effect server-side, unchanged from round 2: `sync_apply_row`'s `insert`/`update` branches share one uniform per-table upsert (§1) — now on an even firmer footing, since *both* op payload types are provably complete by the identical mechanism, not just assumed-complete-by-construction for one of them. Side benefit, not a separate change: this also closes a latent LWW "column-tearing" risk — a partial-payload upsert that won LWW would previously have refreshed only the columns present in that particular payload, leaving other server-side columns stale even though the row as a whole was accepted as newer; a full-row payload updates all columns atomically together, every time. Cost: one extra indexed-by-primary-key `SELECT` per queued insert or update, inside a transaction that's already open — negligible at Beta's single-small-shop scale (this now applies to the higher-volume op, insert, not just update — still well within the ~25KB/50-row push-batch estimate already given in §4, since rows here are a handful of columns, not large).

**Delete-payload ownership fix (Codex-flagged, round 4).** The `permissions` case above needs one extra local `SELECT` for its `roleId` (it isn't already sitting in `recordChange`'s params the way `shopId` is) — **deliberately a same-transaction local SQLite read, never a server-side lookup-by-`rowId`.** A server-side "look up this row's current `shop_id`/`role_id` in Postgres by id" alternative was considered and rejected: (1) it would be ambiguous or unsafe for a row that hasn't reached Postgres yet (a delete pushed before its own insert has landed, or a create-then-delete that never synced the insert at all — not a hypothetical, `seq` ordering guarantees local consistency but says nothing about what's already landed server-side) — "not found" would need an arbitrary default, and defaulting to *allow* would be an authorization bypass; (2) more fundamentally, it would make authorization depend on already-stored server state instead of an explicitly-asserted, JWT-checked claim, which is a weaker trust model than every other op in this design uses. The local re-read has neither problem: local SQLite is always fully consistent (the row and its `role_id` exist locally before anything is ever enqueued), so there's no ordering dependency and no ambiguous-lookup case to default on.

**A real, pre-existing bug this retrofit must fix, not just work around.** Today's write sites are genuinely inconsistent about timestamp format: fresh INSERTs default to `sql\`(current_timestamp)\`` (SQLite-native, e.g. `2026-08-13 10:00:00`, space-separated, no milliseconds); explicit UPDATEs in `sales.ts`/`purchases.ts`/`customers.ts` also use `sql\`current_timestamp\``; UPDATEs in `auth.ts`/`staff.ts`/`settings.ts` use `new Date().toISOString()` (`2026-08-13T10:00:00.123Z`). This isn't cosmetic — **comparing those two formats lexicographically is not reliably order-preserving** (`' '` sorts before `'T'` in ASCII, so a same-day SQLite-native timestamp always sorts "less than" an ISO one regardless of actual time-of-day). Postgres itself is unaffected (its `updated_at` is real `timestamptz`, compared as a timestamp, never text) — but `applyRemoteRow`'s local "is remote newer than local" check, run in JS against today's mixed data, would be wrong. Every write site this task touches gets normalized to `stampUpdatedAt()`'s `toISOString()` for both `updatedAt` and (on insert) `createdAt`, and `applyRemoteRow`'s comparison uses `new Date(x).getTime()`, never string `<`/`>`. Called out again in Risks.

**Case conversion.** DEVELOPMENT_RULES.md: DB columns snake_case, Drizzle/TS fields camelCase. `sync_queue.payload` must already be snake_case before it's stored (the Edge Function passes it straight into `sync_apply_row` with no further transformation), so `toSnakeCasePayload()`/`toCamelCaseRow()` (two small functions, same file) do the one conversion this boundary needs — snake_case going out via `recordChange`, camelCase coming back in via `applyRemoteRow`.

**Ordering.** Push must apply rows in stable, monotonic order — `created_at`/`updated_at` alone can collide (several rows from one checkout share a timestamp), and child rows (`sale_items` → `sales.id`) must reach Postgres after their parent given mirrored FK constraints. **Resolved with an explicit `seq` column**, not SQLite's implicit `rowid`. Rowid was considered and rejected: SQLite's `DEFAULT` clause cannot express a correlated `(SELECT MAX(seq)+1 ...)`, so there's no way to make it automatic at the schema level; every ordered query would need to drop into raw SQL to reference an ORM-invisible column, spreading a SQLite-only detail through `sync/push.ts`/`pull.ts`; and this codebase already has a proven idiom for exactly this — `sales.ts`/`purchases.ts` compute `INV-{year}-{count+1}`-style sequence numbers via a `SELECT MAX(...)` read inside the same transaction. `recordChange`'s `nextSeq(tx)` reuses that idiom.

**Round 8 audit: this migration already shipped.** `apps/mobile/db/migrations/0004_deep_boomer.sql` already exists and already does exactly this — drops `sync_queue_shop_status_idx`, adds `sync_queue.seq integer default 0 not null`, recreates the index as `(shop_id, status, seq)`. There is nothing left to build here. **Migration `0004` is taken; any genuinely new SQLite migration this plan still needs is `0005`, not `0004`.** No backfill risk applied in practice either, matching the reasoning above — the column shipped with a harmless constant default.

```
sync/supabaseClient.ts   — the ONE createClient() call in the app
```

- **`supabaseClient.ts`** — the shared client, `auth.storage` pointed at a **dedicated third MMKV instance** (`createMMKV({ id: 'muthoy-supabase-auth' })`), deliberately separate from `sessionStore.ts`'s existing `muthoy-session` instance. This doesn't violate DECISIONS.md's "MMKV holds session only, never a PIN or hash" entry — it's a different instance entirely holding a Supabase JWT (a categorically different secret from a PIN/hash), and it's required infrastructure: without persistence, the phone would need to re-verify OTP on every app restart, defeating the point of a background sync identity that outlives the one-time OTP challenge. Also exports `handleAppStateChangeForAuthRefresh(status)` (wraps `supabase.auth.startAutoRefresh()`/`stopAutoRefresh()`), called from `app/_layout.tsx`'s *existing* `AppState` listener — keeping "only `sync/` talks to Supabase" intact even for this lifecycle plumbing.
- **Why `sync/` (not a new `auth/`) houses OTP** — flagging the judgment call: OTP unavoidably talks to Supabase (`auth.signInWithOtp`/`verifyOtp`), and splitting "Supabase auth calls" into a separate folder from "Supabase data calls" would mean two folders both constructing/holding a client — more surface for the "only one place talks to Supabase" rule to erode later. One shared client, one boundary; screens only ever call named functions in `sync/otp.ts`/`sync/linkDevice.ts`, mirroring how they never touch raw Drizzle, only named `db/*.ts` functions.
- **Cursor storage lives in `sync/cursorStore.ts`, not `state/`.** Mirroring `sessionStore.ts`'s *technique* (small MMKV-backed get/set), not its *location* — `state/`'s stated purpose is Zustand session/cart/UI state read by component renders; the pull cursor is never read by a render (unlike `session`, which drives `RootSessionGate`), it's sync-internal bookkeeping nothing outside the engine touches. Keeping it inside `sync/` keeps the engine self-contained. **Stores the composite cursor object** (`{ updatedAt, tableName, rowId } | null`), per the pagination fix — not a bare timestamp.
- **`push.ts`** — batch size **50**, matching this codebase's own existing `SEARCH_LIMIT = 50` convention (already used for FTS5 search caps) rather than an arbitrary number — at roughly 500 bytes/row that's a ~25KB request, comfortably small on 2G/3G. Reads via `listPendingSyncRows(50)` (ordered by `seq`), POSTs to the `push` action, maps results back via `markSyncRowSent`/`markSyncRowPermanentFailure` (no retry — a unique-violation hits the same constraint every time)/`markSyncRowTransientFailure` (bumps `attempts`, schedules the next attempt via `backoff.ts`). Loops while pending rows remain and the last batch succeeded network-wise.
- **`backoff.ts`** — `computeBackoffMs(attempts) = min(5000 * 2^(attempts-1), 300000)`: base 5s, ×2, capped at 5 minutes, **8 attempts** before a still-failing row goes terminal (≈15 minutes of accumulated retrying — long enough to ride out a real outage, short enough to surface same-day). Pure, framework-free, unit-tested (`backoff.test.ts`).
- **`connectivity.ts`** — NetInfo listener, triggers a push on the offline→online transition.
- **`scheduler.ts`** — a 120s interval while the app is foregrounded, as a backstop for anything a fire-and-forget trigger missed; **skips the tick entirely when NetInfo reports offline**, avoiding a doomed network attempt every 2 minutes on a dead connection.
- **Trigger wiring happens at the screen layer, not inside `db/`** — this mirrors the *actual* notifications precedent exactly, not just its spirit: `checkout.tsx` today calls `runNotificationChecks` itself, right after `createSaleTransaction()` resolves, not from inside `db/sales.ts`. `triggerSyncNow(shopId)` (fire-and-forget, errors swallowed) is added the same way, at the same call sites: `checkout.tsx`, `inventory/add-medicine.tsx`, `inventory/batches.tsx`, `suppliers/purchase-create.tsx`, `credit/credit-sales.tsx`, `credit/customer-detail.tsx`, `staff/management.tsx`, `settings/settings.tsx` — right after each screen's existing write call resolves. Keeps `db/` and `sync/` from depending on each other. Known tradeoff, already accepted by the precedent it mirrors: a new write call-site must remember to add the line.
- **`pull.ts`** — reads `cursorStore.getLastPulledCursor()`; **`null` now branches into a genuinely different code path (round 9) — full hydration and incremental pulls are no longer the same loop with the same per-page-apply behavior.** Both still call the same `pull` action and the same `sync_pull_changes` (§1, purely `(updatedAt, tableName, rowId)`-ordered, table-unaware) — the split is entirely client-side:

  **Incremental** (`cursorStore.getLastPulledCursor()` returns non-null) — unchanged from round 3: loop `pull` while `hasMore`, apply each page's rows immediately via `db/sync-helpers.ts`'s `applyRemoteRow()`/`applyToTable()` (one transaction per page), persist `nextCursor` after every page (never only at the end), leave the stored cursor untouched on an empty page. **Never `recordChange`** — no code path connects a pulled row back into `sync_queue`, so a pull can never re-enqueue a push, regardless of which path below applied it.

  **Full hydration** (`cursorStore.getLastPulledCursor()` returns `null`) — new two-phase discover-then-apply, replacing round 7's server-side rank ordering:
  1. **Discover**: loop `pull` with `since` starting `null`, exactly like the incremental loop mechanically, but instead of applying each page, append its `changes` to an in-memory array and track the latest `nextCursor` locally (not yet persisted to `cursorStore`) until a page returns `hasMore: false`.
  2. **Stage + apply**: sort the *complete* buffered array by a new client-only constant, `HYDRATION_TABLE_ORDER` (the same 21-table topological order round 7 put in Postgres — round 8's audit already verified it against the real FK graph, see §1's corrected chain reasoning — now living only in `apps/mobile/db/sync-helpers.ts`, exported alongside `TABLE_REGISTRY`, one more small constant on the same already-precedented client/server duplication `_shared/tables.ts` already has for `SYNCED_TABLES`). Apply every row in that sorted order via `applyRemoteRow()`/`applyToTable()`, chunked into transactions of a bounded size (reusing the existing 50-row batch convention from `push.ts` for consistency) — chunk boundaries can't violate FK order, since the entire buffer was already globally sorted before chunking began.
  3. **Persist cursor**: only once every buffered row has been applied successfully, persist the final discovered `nextCursor` as the new durable watermark — this single write is what promotes the device from "hydrating" to "on ordinary incremental sync" from then on.

  **Crash/replay idempotency (both paths):** the durable cursor is never written mid-hydration — only discovery happens before it, and discovery has no side effects, so a crash or connectivity loss at any point during discovery *or* apply simply means the next attempt calls `pull` again with `since: null` and starts over. This is always safe, not just tolerable: every apply is independently idempotent (`applyRemoteRow`'s upsert-by-`id` + LWW `<` guard, and `audit_logs`' `ON CONFLICT DO NOTHING`), so re-discovering and re-applying rows a prior partial attempt already applied is a no-op or a harmless identical rewrite, never a duplicate or corruption. The durable cursor is a single atomic "hydration complete" marker, not an incrementally-trusted progress counter — there is no partial/inconsistent durable state ever observable from outside a hydration attempt. Incremental crash-safety is unchanged from round 3 (per-page persistence, same upsert-by-id idempotency).

  **Accepted residual risk, stated explicitly rather than silently dropped**: round 7's ordering fix also incidentally closed a rarer *incremental*-pull case — a newly-created parent+child pair from another device, where the parent's `updated_at` gets bumped past the child's by a later edit, could apply out of FK order within one page. Reverting to a purely monotonic incremental cursor reopens that narrow case for the incremental path only (full hydration is unaffected — the two-phase design above closes it unconditionally). This requires two devices live on one shop, which Beta's single-device-per-shop scope already excludes — same risk class, and same acceptance reasoning, as the already-accepted stock-quantity-LWW and cross-device-clock-skew risks below. Not fixed by this round; flagged per rule 11.

  Triggered on app foreground (if online), after every successful push cycle, and on the same 120s interval.
- **Stuck-sync notification.** `stuckNotification.ts` checks `countFailedSyncRows(shopId) > 0` after each cycle — a row only reaches terminal `failed` via an immediate permanent rejection or exhausting the 8-attempt retry budget, both already "genuinely stuck," so no separate time threshold is needed on top. `notifications.type`'s enum already includes a `'sync'` variant (anticipated, unused until now) — no schema change needed. De-duplicated the same way `notifications.ts` already de-dupes low-stock alerts (an unresolved-alert check before creating a new one), calling the existing `createNotification(shopId, 'sync', 'warning', 'Sync issue', '<n> change(s) could not reach the cloud yet')`.

Deliberately **not** part of any `recordChange`/`sync_queue` payload and never present in a pull's `row_data` — it's local device-vs-cloud reconciliation bookkeeping, not shop business data, and Postgres has no matching column. Verified safe against the pull-apply path: `upsertRemoteRow`'s `.onConflictDoUpdate({ set: row })` only sets columns that are keys of `row` (built from the server's JSON payload); since `cloudLinkedAt` is never a key of that payload, a pull-triggered update of an already-hydrated `shops` row cannot ever clobber a locally-set value back to null.
2. **`otp-verify.tsx`**: right before `router.replace("/")`, on **either** successful branch (new-registration-after-`linkDeviceToShop`, or restore-after-`pullChanges`), stamp `cloudLinkedAt = new Date().toISOString()` on the local `shops` row via a plain local `UPDATE` (no `recordChange` — this column doesn't sync). Adds a **third branch** to `handleVerify`, reachable only via a new `resumeShopId` param (see next point) — when present, skip both the "create new" and "restore/hydrate" branches entirely and go straight to `linkDeviceToShop(resumeShopId)` after OTP verification succeeds. This is what prevents the crash-recovery path from calling `createShopAndOwner` a second time and duplicating the shop.
3. **`getRegistrationStatus()`**: add a check that runs **before** the existing `pinSetAt` check — if a local owner row exists and `shops.cloudLinkedAt is null`, return `{ status: 'link_pending', shopId, userId, phone }` regardless of `pinSetAt` (covers a crash at any point after `createShopAndOwner`, whether pin-setup has already run or not — a normal, non-crashed registration always completes `linkDeviceToShop` *before* ever navigating to pin-setup, so this new branch never fires on the happy path). `RootSessionGate` routes `'link_pending'` to `otp-verify.tsx` with `{ resumeShopId: shopId, phone }` — a fresh OTP is always required to re-authenticate (deliberately simpler than trying to detect/reuse a possibly-still-valid persisted session; a small added step for a rare recovery path, not worth the extra complexity of session-validity probing). After a successful resume-link, normal routing resumes (`pinSetAt` still null on a very-early crash → pin-setup; already set → dashboard).

**Not in scope**: `role-select.tsx` (unrelated, already an explicitly-deferred unreachable stub).

## Risks (flagging before building, per rule 10/11)

- **[TOP RISK, round 8] This document no longer matches the repo it describes.** A comprehensive audit found a substantially-implemented sync engine already in the repo (`sync-helpers.ts`, `apps/mobile/sync/*`, `otp-verify.tsx`, migration `0004`, four dated 2026-08-13 DECISIONS.md entries) despite this document being maintained under repeated "plan only / do not implement" instructions. One concrete naming divergence was found (`applyToTable` in real code vs. `applyRemoteRow` in this document), meaning the real implementation may reflect an earlier or different version of the design than rounds 3-7 converged on. **Not resolved by this round** — resolving it requires a dedicated line-by-line diff of the live `sync-helpers.ts`/`sync/push.ts`/`sync/pull.ts`/`backend/supabase/` code against rounds 3-7's specific fixes (table-rank pull ordering, `audit_logs` SQL branch, RPC `REVOKE`/`GRANT`, per-row push authorization, insert/update full-row re-read), which is out of scope for this audit pass and needs explicit direction on how to proceed.

- **Mixed timestamp formats already in the codebase** (§3) — a genuine pre-existing correctness bug, not cosmetic: `sql\`current_timestamp\`` (SQLite-native) and `new Date().toISOString()` (ISO) don't compare correctly as strings. Fixed by this retrofit at every site it touches, via `stampUpdatedAt()` + `Date`-based (never string) comparison in `applyRemoteRow`.
- **Trigger vs. LWW** — resolved by omitting the generic `set_updated_at()` trigger entirely for synced tables (§1).
- **Secondary-uniqueness collisions** (`sales`/`purchases` invoice numbers, `batches`' `(medicine_id, batch_no)`, `cash_drawer`'s one-row-per-day) — two competing INSERTs with different ids, not an update LWW can resolve. Resolved by mapping Postgres `23505` to a `permanent` per-row rejection (§2), never blocking the rest of the batch, surfaced via the stuck-sync notification. Accepted low-probability Beta risk — PROJECT_CONTEXT.md's own non-goal is "no real-time multi-device collaboration," Beta is single-device-per-shop.
- **Pull re-enqueue loop** — resolved structurally: `applyRemoteRow` never touches `sync_queue`, so there's no code path by which a pull could generate a push (§4).
- **Pull pagination unsafe at page boundaries when rows share a timestamp** (Codex-flagged) — the original `updated_at > cursor` filter could permanently skip sibling rows sharing the exact page-boundary timestamp. Resolved with a composite `(updated_at, table_name, row_id)` cursor and Postgres row-wise tuple comparison, which has no possible ties (§1/§2/§4) — chosen over a server-assigned global monotonic sequence (the SQLite-side `seq` idiom) as the simpler fix that directly answers what was asked, without a new schema column across all 21 tables.
- **Residual, explicitly accepted (not fixed by the above): cross-device clock skew during incremental (non-full) pulls.** The composite cursor solves *ties within one pull cycle*; it does not solve a *different* device with a skewed clock later pushing a row whose client-stamped `updated_at` is earlier than a cursor another device has already advanced past — that row would never be returned to the already-advanced device by an incremental pull (it would only be picked up by a fresh full hydration). This is a pre-existing characteristic of using client-stamped `updated_at` as the pull ordering key at all, not something introduced by this fix, and it is the same class of risk as the already-accepted stock-quantity LWW risk below: real only if two devices are both live for one shop, which Beta's single-device-per-shop scope (Volume 0) rules out. Flagging per rule 11 rather than silently declaring it solved; would need a server-assigned monotonic column (deferred, see above) if it ever needs closing before a multi-device pilot.
- **Outbox update payloads could be partial, but Postgres's upsert needs a complete row** (Codex-flagged) — several real call sites (`changeOwnPin`, `resetStaffPin`, `deactivateStaff`) only `UPDATE` a few columns, which previously would have been enqueued as-is and could fail or null out data server-side. Resolved: `recordChange` re-reads the full row from SQLite, same transaction, immediately after the caller's `UPDATE`, for every `update` op (§3) — call sites are unaffected. Side benefit: also closes a latent LWW column-tearing risk where a partial payload winning LWW would leave untouched columns stale.
- **Shop-id spoofing** — resolved by the Edge Function rejecting any request where the JWT's `app_metadata.shop_id` doesn't match the request body's `shopId` (§2), independent of RLS since the service-role path bypasses RLS entirely. (Per-row, per-table breakdown — including the two tables without a plain `shop_id` column — in the next bullet.)
- **`audit_logs` append-only guarantee didn't survive the `SECURITY DEFINER` path** (Codex-flagged) — RLS's insert/select-only policy on `audit_logs` is invisible to `sync_apply_row` (RLS is bypassed by definition for `SECURITY DEFINER`), and the insert/update collapse (above) would otherwise have let a client silently rewrite existing audit history via a push. Resolved by keeping `audit_logs` as the one non-unified branch: `insert` only, `ON CONFLICT DO NOTHING` (never modifies an existing row), `update`/`delete` raise `MU001` and are mapped to a permanent (never retried) push rejection (§1/§2).
- **`sync_apply_row`/`sync_pull_changes` callable directly by any client holding the anon key** (Codex-flagged) — both are `SECURITY DEFINER`, and Postgres grants `EXECUTE` to `PUBLIC` by default on function creation; unrevoked, this would let a client call either RPC directly, bypassing every Edge-Function-side authorization check (§2) entirely, on a path RLS also can't reach (RPC calls don't go through table policies). This was a real, previously-undocumented gap in the "two enforcement layers" framing — there were structurally three paths into Postgres (direct table PostgREST, service-role-via-Edge-Function, direct RPC PostgREST) and only two were guarded. Resolved with explicit `REVOKE ... FROM public, anon, authenticated` / `GRANT ... TO service_role` on both functions, in the same initial migration (§1). Confirmed compatible with the Edge Function's own `.rpc()` calls, which authenticate as `service_role` and are unaffected.
- **Full-hydration/pull row order had no relationship to FK dependency order** (Codex-flagged, round 7; **corrected round 9**) — round 7's fix (reprioritizing the durable cursor to `(table_rank, updated_at, row_id)`) solved full hydration but broke incremental sync: `table_rank` is a static per-table attribute, not a monotonically-increasing quantity, so once a device's cursor advanced past a high-ranked table, any *future* write to a lower-ranked table would sort behind the stored cursor and be **permanently, silently skipped** — a durable watermark must be monotonic in real time, and `table_rank` isn't. **Round 9 fix: split the two concerns.** The durable/incremental cursor reverts to round 3's pure `(updated_at, table_name, row_id)`, table-unaware, in `sync_pull_changes` (§1) — safe forever, never falls behind. FK-safe apply order becomes a **client-side, hydration-only** concern (§4): full hydration discovers all pages into an in-memory buffer first (no durable cursor written yet), then applies the complete buffer in one client-sorted FK-safe pass (`HYDRATION_TABLE_ORDER`, the same verified 21-table order round 7 derived, now living client-side only), then persists the cursor as a single atomic "hydration complete" marker. Ordinary incremental pulls are untouched — per-page apply, per-page cursor persistence, exactly as round 3. `PRAGMA foreign_keys` is still never touched. Crash/replay at any point is safe by restarting hydration from `since: null` — every apply is independently idempotent. **Accepted residual, not fixed**: the narrower incremental-only case round 7 also happened to close (a newly-created parent+child pair whose parent gets edited again before this device's next incremental pull) is reopened by this revert — real only under multi-device use, which Beta's single-device-per-shop scope already excludes; same acceptance class as the stock-quantity-LWW and clock-skew risks below.
- **[Round 10, CRITICAL, confirmed live] Cross-tenant row hijack via push** — `sync_apply_row`'s upsert/delete `WHERE` clauses check only `updated_at`, never the existing row's `shop_id`, so a payload's self-declared `shop_id` was being trusted as sufficient authorization to mutate *any* row by id. Fixed by adding `p_caller_shop_id` to the RPC and an ownership predicate (`shop_id = p_caller_shop_id`, or the `shops`/`permissions`-equivalent) to every upsert/delete `WHERE` clause (§1).
- **[Round 10, CRITICAL, confirmed live] link-device tenant takeover** — checked only the caller's own current claim, never whether the target `shopId` was already claimed by someone else. Fixed with a `shop_claims` first-claim-wins table, atomically inserted on first successful link, checked (not just the caller's own state) on every subsequent call (§2).
- **[Round 10, HIGH, confirmed live] Same-batch push rows aren't held back by an earlier failure** — self-corrected only incidentally via generic Postgres FK-violation retries, with zero protection for polymorphic no-FK columns. Fixed by making the Edge Function stop processing a batch at the first non-`applied` row, returning `'skipped'` (treated as transient) for the rest (§2).
- **[Round 10, HIGH, confirmed live] FK existence alone permits cross-shop references** — every FK in the schema checks existence only, not tenant match. Fixed with a shared `assert_fk_same_shop` guard invoked per relevant FK column inside each table's branch, `MU003` on violation (§1). `payments.party_id`/`ref_id` (polymorphic, no FK) remain an accepted, explicitly-flagged gap.
- **[Round 10, CRITICAL, confirmed live] Registration crash recovery: no durable cloud-link tracking** — a crash between local shop creation and `linkDeviceToShop` strands the shop permanently, unsynced, with no user-visible signal, confirmed by full trace of `RootSessionGate`/`getRegistrationStatus()`. Fixed with a new local-only `shops.cloudLinkedAt` column, a `getRegistrationStatus()` check that runs before the `pinSetAt` check, and a `resumeShopId`-driven third branch in `otp-verify.tsx` that re-links the *existing* local shop rather than creating a new one (§5).
- **Insert outbox payloads could omit DB-defaulted/computed columns** (Codex-flagged) — the original design trusted a caller's pre-`INSERT` values object as "already complete," but SQLite fills in schema defaults (`createdAt`, `isDeleted`, etc.) for columns real call sites legitimately omit, so the pre-write object and the actually-persisted row could differ — risking either a missing NOT NULL column or a client-guessed explicit `null` reaching Postgres. Resolved by giving `insert` the exact same post-write, same-transaction re-read `update` already had (§3) — `recordChange` now has one completeness rule for insert+update (re-read what SQLite actually persisted) and one for delete (§3 round 4's ownership-aware markers).
- **`applyRemoteRow`'s stale-write guard was never reconciled with the `audit_logs` append-only fix** (Codex-flagged) — the original generic LWW-guarded upsert, applied uniformly, would have let a pulled `audit_logs` row overwrite a local one via `DO UPDATE` whenever its `updated_at` looked newer, contradicting the append-only guarantee round 5 already established server-side. Resolved: `applyRemoteRow` now dispatches on `table` — `audit_logs` uses `ON CONFLICT DO NOTHING` (mirrors `sync_apply_row`'s server-side branch exactly, no timestamp comparison since audit_logs is never legitimately updated on either side); every other table (including `shops`/`permissions`, which need no extra branch here — their scoping is already enforced upstream by pull's filter) uses the generic `local.updatedAt < remote.updatedAt` guard, now made explicit as covering all 20 of them via the shared `TABLE_REGISTRY`, not just the one example table the original sketch showed.
- **Delete payloads had no ownership field for push authorization to check** (Codex-flagged, found during partial implementation) — the original "minimal delete-marker fields only" contract (`id`/`deletedAt`/`deletedBy`) meant a delete op had nothing matching insert/update's `payload.shop_id`/`payload.id`/`payload.role_id` checks (§2), so the same-rules-for-every-op requirement was structurally unsatisfiable as originally designed. Resolved by giving delete payloads the same three-category ownership field as insert/update (§3's `buildDeletePayload()`): normal tables get `shopId` (already available, free); `shops` uses its own `id`; `permissions` gets a same-transaction **local** SQLite re-read of `roleId` — deliberately not a server-side lookup-by-id, which was considered and rejected (ambiguous for a not-yet-pushed row, and it would make authorization depend on prior server state rather than an explicitly-asserted, JWT-checked claim). `audit_logs` is unaffected — its `delete` op is already rejected outright at the SQL layer, before authorization would run. **Compatibility check (LWW / soft-delete replication / pull / FK ordering):** LWW unaffected — soft-delete still uses the identical `updated_at`-guarded `UPDATE`, the new fields are authorization-only and never written to a column. Pull unaffected — `sync_pull_changes` always returns full rows straight from Postgres regardless of what a push payload looked like, so replication of a soft-deleted row's shape was never the gap. FK ordering unaffected — the local re-read is against already-consistent local SQLite state, with no dependency on what has or hasn't reached Postgres yet (this is precisely what made the rejected server-side-lookup alternative ordering-unsafe, and the chosen local-read alternative ordering-safe).
- **Push authorization for tables without a plain `shop_id` column** (Codex-flagged) — `shops` (no `shop_id`; the row *is* the shop) and `permissions` (no `shop_id`; only `role_id → roles.shop_id`) would silently break or misauthorize under a naive uniform `payload.shop_id === callerShopId` check — `shops` payloads have no such field (every row would wrongly fail), and `permissions` has nothing to check at all. Resolved with three explicit, per-table rules mirrored identically across RLS (§1), push authorization (§2), and pull's `sync_pull_changes` filter (§1): normal tables compare `shop_id`; `shops` compares its own `id`; `permissions` joins through `roles`. Also added a universal `rowId === payload.id` push-side integrity check for every table (pull needs no equivalent — `row_id` and the `id` inside `row_data` are structurally the same value by construction, both read from the same row in the same query). The `permissions` role→shop check runs **per-row, not once per batch** — see §2 — specifically so it stays correct when a `roles` row and a `permissions` row referencing it arrive in the same push batch; an upfront batch-level check would race the not-yet-applied `roles` insert and wrongly reject a correctly-ordered row.
- **Restore-on-new-phone / duplicate-shop hazard** — an unconditional "always call `createShopAndOwner` after OTP verify" would silently fabricate a duplicate empty shop for a phone that already owns one. Resolved by branching on the verified session's existing `app_metadata.shop_id` before deciding whether to create-and-link or hydrate-and-restore (§5).
- **Token staleness after `link-device`** — the client's in-hand JWT doesn't reflect a just-set `app_metadata.shop_id` until refreshed. Resolved by an explicit `refreshSession()` call before any sync call is allowed to fire (§5).
- **Stock-quantity LWW is a genuine, already-accepted Beta risk**, not introduced by this plan — Volume 0's own words: "safe for the realistic beta scenario... a genuine risk if two devices ever edit the same shop's stock offline at the same time... do not run a multi-device pilot before [delta-merge] ships."
- **Once OTP ships, local development of every other feature requires a live, configured Supabase project + SMS provider**, since registration becomes the front door to creating any test shop. A direct, accepted consequence of replacing the local-only flow, not an oversight — flagged rather than quietly inventing an undocumented dev-mode bypass (which would itself violate rule 11/9).
- **SQLCipher gap** — still open, logged elsewhere, not this plan's job, flagged so it isn't forgotten now that sync makes real cloud round-trips a reality.
- **Live OTP testing is not verifiable by this plan alone** — needs a manually-configured Supabase project + SMS provider (see Prerequisites).

## Verification

Mirrors Volume 0's own Day 13 checklist, plus additions this design surfaced:

1. **10 offline sales → online → Supabase.** Airplane mode, 10 checkouts (confirm expected `sync_queue` rows via direct SQLite inspection). Reconnect, confirm all 10 sales + line items + inventory movements appear in Postgres, matching exactly (paisa integers, not scaled).
2. **Real OTP registration.** Register with a real phone against a live, configured Supabase project + SMS provider (external precondition). Confirm `link-device` sets `app_metadata.shop_id`, and a push attempted right after succeeds (not rejected on a stale token, per the refresh-session fix).
3. **LWW correctness, both directions:**
   - *Push:* edit a row locally (older `updated_at`) while Postgres's copy has a newer one (simulating another device) → push → confirm Postgres **keeps** its newer value.
   - *Pull:* edit a row locally (newer), pull a deliberately-older remote version of the same row → confirm local SQLite is **not** overwritten.
   - Include a stock-quantity field in at least one of these — not just an arbitrary column.
4. **Kill mid-sync**, reopen → confirm no `sync_queue` row is lost or left stuck neither sent nor retried (duplication is structurally impossible given upsert-by-`id`).
5. **Secondary-uniqueness collision** (e.g. two offline "devices" both create today's `cash_drawer` row) → confirm the losing row ends `failed` with a descriptive `lastError`, the batch and app are unaffected, and a stuck-sync notification appears.
6. **Restore-on-new-phone.** With an already-synced shop from steps 1-5, install fresh (or clear app data), register with the *same* phone, verify OTP, confirm the app detects the existing `app_metadata.shop_id`, runs a full-hydration pull instead of creating a duplicate shop, and lands on PIN login (not PIN setup) with all prior data present.
7. **Second owner, same device** (rule 7, extended) — register a second, different shop on the same physical device with a different phone number; confirm its sync traffic authenticates as the second owner, never the first, and neither shop's local data is visible to the other.
8. **Full offline day → sync** — open cash, several sales, an expense, a credit collection, then sync → confirm the Postgres copy matches the local copy exactly, including `cash_drawer`.
9. **Pull pagination tie-break.** Force a page boundary to land mid-tie: seed enough rows sharing an identical `updated_at` (e.g. a single fast batch of `stampUpdatedAt()` calls landing in the same millisecond) that they span across a `p_limit`-sized page split → pull with a small test page size → confirm every tied row is returned exactly once across pages (none skipped, none duplicated), verified by comparing the full pulled-id set against the full source-id set.
10. **Partial-update payload completeness.** Trigger a narrow local `UPDATE` (e.g. `changeOwnPin`, which only touches `pinHash`/`pinSetAt`/`updatedAt`) on a row that has **not yet been pushed** (no prior `insert` op reached Postgres) → push → confirm `sync_apply_row`'s `INSERT ... ON CONFLICT` does not error on a missing NOT NULL column and the row lands in Postgres with every other column correctly populated (not null/default), proving the outbox payload was the full row, not the partial `.set()` values.
11. **`audit_logs` append-only under a hostile push.** Using a test harness (not the app UI — the app never issues this), push a crafted `{ tableName: 'audit_logs', op: 'update', rowId: <existing audit log id>, payload: {...} }` directly to the `push` action → confirm the row is rejected with `reason: 'permanent'` (SQLSTATE `MU001`) and the existing Postgres row's columns are byte-for-byte unchanged afterward. Also push a duplicate `insert` of an already-applied audit log id → confirm it no-ops (`ON CONFLICT DO NOTHING`) rather than erroring or altering the row.
12. **RPC privilege lockdown.** Using the anon key directly (no Edge Function, e.g. `curl .../rest/v1/rpc/sync_apply_row` or `sync_pull_changes` with a valid OTP-issued JWT), attempt to call either function → confirm Postgres rejects with a permission-denied error, never executes, regardless of how well-formed the arguments are. Repeat once more confirming the Edge Function's own calls (via the service-role key) still succeed unaffected.
13. **Delete-authorization contract.** Push a legitimate soft-delete (e.g. deactivate/soft-delete a `customers` row) → confirm the enqueued `sync_queue` payload contains `shop_id` (not just id/delete markers), and the row is applied server-side. Then, using a test harness, push a crafted delete payload with `shop_id` set to a *different* shop's id (or, for a `permissions` row, a `role_id` belonging to a different shop) → confirm `reason: 'permanent'` rejection, and the target row's `is_deleted`/`deleted_at` are unchanged in Postgres.
14. **Insert payload completeness.** Trigger a real insert that relies on at least one schema-defaulted column (e.g. a fresh `createCustomer` row, relying on `isDeleted`'s default rather than the caller setting it explicitly) → inspect the enqueued `sync_queue` payload directly (SQLite) → confirm it contains the actual persisted values for every column, including the defaulted one(s), never an omitted field or a synthesized `null` — then push → confirm Postgres's row matches exactly.
15a. **Full-hydration FK order (round 9: two-phase design).** On a fresh (or cleared) device, with a shop that has data across multiple dependency levels (e.g. a purchase creating a batch, a sale referencing that batch, a credit against that sale), run full hydration (`since: null`) with a deliberately small test page size that forces many discovery-phase page boundaries mid-chain → confirm discovery completes (no apply attempted yet) → confirm the apply phase, chunked in bounded transactions, never raises a foreign-key-constraint error, and (via logging/trace) that no table's row is applied before all rows of every table it depends on → confirm the durable cursor is only written once, after the last chunk applies successfully. Also run a topological-validity assertion offline: walk `apps/mobile/db/schema.ts`'s actual FK declarations and confirm every FK's target table has a strictly lower position in `HYDRATION_TABLE_ORDER` than its source table.
15b. **Incremental durable-cursor monotonicity (round 9, the bug this round fixes).** Complete hydration on a device, letting its cursor advance through several sync cycles including at least one touching a high-ranked table (e.g. `audit_logs` or `cash_drawer`). Then, from another device, create a genuinely new row in a low-ranked table (e.g. `medicines`) → run this device's next incremental pull → confirm the new `medicines` row **is** returned and applied, proving the durable cursor never falls behind for a lower-ranked table's future write. (This is the exact failure mode round 7's rank-primary cursor would have produced silently — it must be caught here, not discovered later as a permanently-missing row.)
15c. **Accepted residual: new parent+child on an established device.** On a device already on ordinary incremental pulls, have another device create a new medicine and a batch for it, then edit the medicine again (bumping its `updated_at` past the batch's) before this device's next pull → this is now an *accepted* out-of-scope risk (Beta is single-device-per-shop), so this test documents/confirms the *known* behavior (the batch may apply before the medicine and fail on the FK constraint) rather than asserting it's fixed — useful as a regression check that this failure mode is understood and bounded to the multi-device case, not silently reintroduced elsewhere.
16. **[Round 10] Cross-tenant hijack attempt is rejected.** From shop A's authenticated session, push an `update` for a `rowId` known to belong to shop B (test fixture), with `payload.shop_id` set to shop A and a newer `updated_at` than shop B's row → confirm the push is rejected (not silently `'applied'`) and shop B's row is byte-for-byte unchanged in Postgres afterward. Repeat for `delete`.
17. **[Round 10] link-device claim-jacking is rejected.** Create shop A normally (real registration, real claim). From a second, unrelated OTP-verified-but-unlinked account, call `link-device` with shop A's id → confirm 403, confirm shop A's `app_metadata.shop_id` linkage (and the `shop_claims` row) still points to the original owner.
18. **[Round 10] Batch ordering under mid-batch transient failure.** Force a transient failure on a low-seq row within a batch that also contains higher-seq, FK-dependent rows (e.g. simulate a timeout on a `sales` insert while its `sale_items` are in the same batch) → confirm the dependent rows come back `'skipped'`, not attempted, and are retried only after the parent succeeds on a later attempt.
19. **[Round 10] Cross-shop FK reference is rejected.** Push a `sale_items` row with a legitimate `shop_id` (shop A) but a `batch_id` belonging to shop B → confirm `MU003` / permanent rejection, and no row is written.
20. **[Round 10] Registration crash recovery.** Simulate a kill between `createShopAndOwner` succeeding and `linkDeviceToShop` completing (test harness, not real crash) → relaunch → confirm `getRegistrationStatus()` returns `'link_pending'`, routing lands on `otp-verify.tsx` with `resumeShopId` set, a fresh OTP re-links the *same* local shop (confirm no second `shops` row was created), and normal pin-setup/dashboard routing resumes correctly afterward.
15d. **`audit_logs` pull-side immutability.** With an audit log entry already applied on one device, simulate a pull returning that same row with a *newer* `updated_at` but different content (a hostile/corrupted server response, via test harness) → confirm the local device's `applyRemoteRow` leaves the existing local row untouched (`ON CONFLICT DO NOTHING` fires, not `DO UPDATE`) — proving pull-side append-only holds independently of timestamp comparison, not merely by coincidence of well-behaved server data.
